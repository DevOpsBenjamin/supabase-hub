# CLAUDE.md

Shared Supabase project for several small apps. One schema per app, one migration
history at the root. Read `README.md` for the layout and `docs/shared-project.md`
for what a shared project costs.

## Hard rules

- Never edit a migration that exists in `supabase/migrations/`. Assume it is
  already applied. Correct it with a new migration.
- Create migrations with `scripts/new-migration.sh <app> "<description>"`. The
  14-digit UTC timestamp and the schema prefix are what keep the history ordered
  and greppable.
- A migration only ever touches its own app's schema.
- Every `create table` is followed, in the same file, by
  `alter table ... enable row level security`, its policies, and its grants. A
  granted table without policies is readable by every app in the project.
- `apps/*/schema.sql` and `apps/*/types/database.ts` are generated by
  `scripts/snapshot.sh` and `scripts/gen-types.sh`. Never hand-edit them.
- Adding a schema means updating `[api] schemas` in `supabase/config.toml` and
  telling the user to mirror it in the dashboard's Exposed schemas. `new-app.sh`
  does the first half only.

## Conventions

- SQL is lowercase, identifiers are `snake_case`, tables plural.
- Schema name is derived, never chosen: `app_` + slug with dashes as underscores.
- Project-wide flat namespaces (storage buckets, edge functions) are prefixed
  with the app slug.
- Everything committed here is in English.

## Do not

- Run `supabase db reset` against anything but the local stack.
- Put a service_role key in an app, an example, or a doc.
- Add a shared "utils" schema for one app's helper. It belongs in the app schema.
